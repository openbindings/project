# Guidance panel: the adversarial reader

Cold read of the decision-procedure draft, 2026-09-19.

## Grades

| Criterion | Grade | One-line justification |
| --- | --- | --- |
| Decidability | C- | Step 0 has no tie-break for ambiguous ground, rule 7 leaves "which consumer" as a free variable, step 1.2's line between "what the language does" and "values" is undefined, and rule 8 can be claimed against any option; a cold reader reaches whichever answer they walked in with. |
| Internal consistency | D+ | Example 12 contradicts the step 3 order (rule 8 is precedence 2, rule 3 is precedence 3, rule 3 wins); rule 4 is "never a tie-break" in step 3 but is a deciding rule in examples 1 and 10; example 4 extends a standing maintainer ruling, which the escalation list says must escalate, and calls it "high"; the incorporated authority `JSON.stringify` is applied in 8c and set aside in 8a with no substitution rule to say why. |
| Generality | C | Heuristics 14 through 17 and 21 through 23 are the JSONata loop's post-mortem in general dress; "class", "member", "ledger", "suite", "the reference", "the stub" are undefined; nothing here tells a loop on a binding specification or an interface contract what "the surface" or "the consumer" is. |
| Escalation boundary | D | "Published" is undefined and the interfaces repo has no tags by design; the standing "ambiguous means OB-side, ask" tie-break is dropped; ground-(a) items still get the procedure's answer applied to the artifact; cross-member and SDK-parity-affecting decisions and security properties never escalate; the "conflict the precedence does not resolve" clause is formally unreachable. |
| Clarity and tone | B- | The prose is good project guidance in register, but "loud", "quiet", "safe", "common", "consumer", "boundary", and "fact" are load-bearing and undefined, and a newcomer does not know what a class README or an apply-bin is. |
| Overall | C- | It fixes the three named defects and introduces a fourth: a procedure whose every value-bearing term is chosen by the person applying it, so it licenses any answer while presenting the answer as "by the procedure". |

## How to game it

**Step 0, classification.** The standing rule this document replaces (the ruling-authority split, 2026-07-11, refined 2026-08-20) says "when genuinely ambiguous which side it falls on, treat it as OB-side and ask." That sentence is gone. In its place: "Only (a) escalates by default", with (c) explicitly including "a binding-specification convention". Every binding-spec ruling in the project's memory was a maintainer ruling; under this text a loop on a binding spec classifies the shared-doctrine question as (c) and decides it. Going the other way, (a) includes "a portability posture", and the numeric model of the evaluator that the OBI transform language depends on is a portability posture by the project's own framing ("transform language pinned for document portability only"), so a loop that wants to dodge 8a through 8c and 10 escalates all four as ground (a). Nothing in step 0 tells these two readers apart.

**Step 1.1, "Quote the text".** Quoting prevents paraphrase, not selection. Example 8a is the proof: the loop's own record says the documentation "is silent on whether the value rounded is the binary float64 or its shortest decimal", and the document converts that silence into rule 1 at confidence "high" by quoting examples and the phrase "financial rounding". Once examples count as authority text, any example in any doc is a precedence-1 trump, and every advocate can find one. The same move in reverse: 8c cites `JSON.stringify` as incorporated authority that "speaks for binary64", while 8a discards `JSON.stringify`'s binary64 value model (under which 2.675 is not a tie and the answer is 2.67). The document has no substitution rule (the loop's 6g/6n drafted one) so "incorporated" means whatever the arguer needs it to mean this row.

**Step 1.2, the reference decides silence.** "What the language does (not about values or the surface)" is the whole game. Regex dialect is what the language does; the documentation is silent (or so the loop believed for six panels); the reference is jsonata-js with a backtracking ECMAScript engine; step 1.2 says adopt it "and do not call it a divergence". That is the opposite of example 4 and it smuggles in catastrophic backtracking, which the security reviewer called the ReDoS decision. Integer-like key hoisting: documentation silent, reference hoists, step 1.2 says adopt; example 1 ships an insertion-ordered `*Object` that does not hoist. `$round(2.675, 2)`: documentation silent (per the loop), reference shifts the decimal string; step 1.2 gives 2.68 at step 1 and the lens never runs. The document applies step 1.2 in none of these and states no test for when it applies. It also never names the reference (which repository, which pinned version) and never carves out behavior the reference has that the project would refuse on security or bound grounds.

**Rules 1 and 2 test.** "Is one option what the authority text says, and the other a guess wearing its name?" Every side claims the first slot. The test has no procedure for deciding whose reading is the text and whose is the guess; it restates the disagreement as a question.

**Rule 3.** "A layer's job" is stated by whoever is arguing. Example 1: "the evaluator does not convert its input" (against uniform `*Object`). Same rule, same case: "the evaluator returns JSONata values; a JSONata object is ordered; an unordered map is the evaluator not doing its job" (for uniform `*Object`). Example 12: "the result domain holds values only" (against a sentinel) versus "absence is a JSONata outcome the language itself names and the layer must carry it" (for one). Rule 3 decides nothing until someone writes down what each layer is for, and the document does not.

**Rule 4.** Step 3 says rule 4 "never break[s] a tie by itself"; examples 1 and 10 list it among the deciding rules. Worse, rule 7 is structurally a "make X the same as Y" argument (make this surface the same as the standard library), so rule 4 can be invoked to nullify any rule 7 argument, and the document does not say which prevails.

**Rule 5.** "Shortest correct common path" requires knowing the common caller. Example 3 takes the performance reviewer's "99% is one goroutine"; the integrator's fan-out sketch is the other 99%. Whoever asserts the population wins rule 5.

**Rule 6.** "Is the unconfigured behavior the safe one?" Safe for whom? RE2 is safe (linear time); the JavaScript dialect is safe (existing expressions do what their authors tested). Refusal is safe (no silent corruption); rounding is safe (no production outage on an inexact operand). Rule 6 is a synonym for "the option I prefer".

**Rule 7 and heuristic 15.** This is the largest hole. "A user of *this kind of surface*" lets the arguer choose the kind: Go standard-library user, JSONata author, JSON consumer, OpenBindings author, jsonata-js port user, Step Functions user. Every one of the twelve questions has at least two consumer kinds with opposite expectations. Heuristic 15 then says a boundary follows its consumer, and lets the arguer decide what is a boundary: example 1 treats `Eval`'s return as inside the evaluator (value function rules, keep the split); example 9 treats `Canonical` as a boundary (consumer rules). Nothing says why `Eval` is not a boundary with a Go caller as its consumer, which yields uniform `map[string]any` by "encoding/json never does this to a caller". Pick the boundary, pick the consumer, pick the answer.

**Rule 8 and the precedence.** "Can this option fail quietly?" is satisfiable for any option, because "quiet" is not defined and every design has a quiet failure story. Since rule 8 sits at precedence 2, above everything but the authority text, the winning strategy under this document is to tell a quiet-failure story about the option you dislike. The document does this itself in example 12: rule 8 "argued for the sentinel and loses at precedence 3", which is impossible under the stated order unless rule 8 is also claimed for the triple, which the row does by relabeling ("can leak into a container, which is the quieter failure"). That is the technique, demonstrated by the author. Example 3 is the same: "scheduling-dependent budget exhaustion" (quiet, reject concurrency) versus "a data race on a shared single-goroutine handle is undefined behavior with no error" (quieter, reject the rule). Example 4: "linear-time matching is loud and predictable" versus "`\s` and case folding differ silently on patterns that compile", which is rule 8's literal text ("different outcomes for one input").

**Rule 9.** "Would two independent implementations that both follow this option agree?" Any option agrees with itself once fully specified; the test measures how many words were written, not which option is right. It is also a universal veto in the other direction ("Go map order is not reproducible, so no option involving a map passes rule 9").

**Rule 10.** "Restate it for the kind" inflates or deflates scope at will. Inflate ("this is really about every numeric conversion in every member") and the question becomes a portability posture or a re-affirmation and escalates; deflate ("this is about one method") and it is (d), decided.

**Rules 11 and 12.** "A wish with no consumer" and "work nobody has asked for": the document does not say whether a panel reviewer's sketch is a consumer. Example 5 needs "the first SDK consumer" after five panels of integrator sketches; example 2 builds `SelectPath` with no consumer at all; example 9 defers struct decoding "until a consumer asks" after the integrator asked in three panels. Reviewers are consumers when the loop wants to build and wishes when it wants to defer. Rule 12's "before anything ships" is always true pre-1.0, so it defers anything, including example 6's language-neutral value model, which the document nonetheless orders built.

**Step 3, "applied only when two tests give opposite answers on the same option".** Frame the two arguments as being about different options and precedence never engages; then either escalate ("a conflict the precedence does not resolve") or pick. The document also never says whether precedence is lexicographic; every row cites three or four rules, inviting the reading that three lower rules outweigh one higher one when that is the answer wanted, and the reverse otherwise. And step 3 is "inferred from the project's rulings to date", which rule 1 says are revisable precedent, not authority; "medium" confidence therefore means "decided by the least authoritative sentence in the document", and the document's invitation to challenge that order is a standing license to re-litigate any medium row.

**Step 4, re-affirmation.** "Extending it to a new instance is a re-affirmation, not a citation" collides with the escalation list's "extending a prior *maintainer* ruling". A loop's own decisions are not maintainer rulings, so they are freely re-decided (and rule 9 then says the inconsistent answers are not a rule); after batch review they become maintainer rulings, so every second use escalates. Either reading is available. Example 4 already trips this: it extends "the standing fidelity-over-coverage ruling" to regex and marks itself "high, decided" instead of escalating.

**Heuristic 13.** "Decide it by the procedure and mark it revisable" plus "a ruling package never stops the loop: the artifact keeps the procedure's answer" means a ground-(a) item is decided too; escalation changes a label, not the artifact. And deferral under rule 11 is pending under another name, so 13 forbids nothing: relabel "pending" as "deferred, no consumer".

**Heuristic 14.** "The class decided, and here is the text" is unavailable when the class text does not exist, which is the state of every first member; the loop writing the class document is deciding for every future member under a heuristic marked "inferred". 14 also outranks rule 7's Go-idiom argument at the value level, but 7 is ratified and 14 is not, and the document does not say which yields.

**Heuristic 16.** "One rule per domain" lets the arguer draw the domain. The loop's own iteration 6 called refuse-on-conversion and round-on-result "two policies"; the same facts are "two domains" (operand conversion, result rounding), each with one rule. 16 cannot tell these apart.

**Heuristic 17.** "Refusal is for what a domain cannot hold at all: overflow past a stated bound." A bound is stated by writing it down; 2^53 is a stated bound (the idiom reviewer: "draw the boundary at 2^53, where `CodeInexact` already draws it"). So 17 licenses 8b's refusal as readily as it forbids it. And "cannot hold at all" versus "inexact" collapses on inspection: binary64 cannot hold 9007199254740993.5 exactly, which is what inexact means.

**Heuristic 18 against heuristic 21.** "The obvious reading" of `Select(ctx, path ...string)` to a Go standard-library user is `filepath.Join(elem ...string)`: one path from many elements. Heuristic 21 says stdlib precedent decides shape; heuristic 18 says the call must mean two fields. The document offers both and no order between them.

**Heuristic 19.** "Give it a job" is an instruction to invent one. The security reviewer's blocking `Close` has a job (end the borrow window); the document deletes it by first deciding example 3 so the job vanishes. Decide the examples in a different order and `Close` survives.

**Heuristic 20.** "A demonstrable case (a wrong example, a contradiction, a law violated)" versus "a preference": a law is demonstrable once someone has written it. The PL skeptic's substitutivity law removed the 2^53 cap in iteration 5 as a fact; the practitioner's restated cap returned in iteration 6, also as a fact. Write the law, then demonstrate the violation, and a preference is a fact.

**Heuristic 21.** Every answer has a standard-library analogue: `bufio.Reader` (single goroutine, no Close), `sql.Rows` (single goroutine, Close), `http.Server.Shutdown(ctx)` (Close takes a context), `regexp` (no Close, concurrent-safe), `sync.Map`. The heuristic names no rule for choosing the analogue, so it decides nothing; and its second sentence duplicates step 1.2 with the same undefined "no value is implicated".

**Heuristic 22.** "Every integrator would otherwise make differently" is established by one reviewer's sketch, and 22 licenses the project to build anything for which such a sketch exists, in direct tension with 11 and 12; the document does not say which set wins when 22 says build and 11 says defer.

**Heuristic 23.** This is "shipped behavior governs" with a disclaimer. The proviso "provided each ledger entry passed the procedure" is checked by the same loop that wrote the ledger, and for the first loop it is unsatisfiable: the ledger predates the procedure, so no entry passed it, yet example 6 invokes 23. An agent under pressure rewrites the doctrine to bless what it did and cites 23. The sentence "This is not 'shipped behavior governs' (it never does)" is an assertion, not a mechanism.

**"What still escalates".** "Published" is the softest word in the document. The interfaces repository has no tags and no changelog by policy, so "a tagged release" never applies there and a new version file is not "a change to a published interface version"; the lens therefore decides new interface versions. The jsonata-evaluator repository is public on GitHub with a Go module path, so `go get` works today; is that published? The spec's working draft is on openbindings.com; published? "Publishes" in the last bullet: is filing a GitHub issue publishing? Pushing a branch? The memory says never push without approval; this document does not. Missing entirely: any decision that changes what the other SDK or a second member must do at the observable boundary (SDK parity is a project commitment, and 8b in Go binds TypeScript); any security property (linear-time matching, bounds); any change to a repository other than the loop's own. And "a conflict the precedence in step 3 does not resolve" cannot occur, because the order is total over rules 1 through 9 and 4, 10, 11, 12 are excluded; the bullet is decoration, or a dodge for whoever frames the tests as being about different options.

**The stopping clause.** "Flips under the procedure in two consecutive iterations" is controlled by the agent: record the same option each iteration and call the change a "refinement" and nothing flips; want to stop, let it flip. The actual loop's 8c went cap, no cap, cap across iterations 4, 5, 6, which under this clause is "a genuine escalation", and the same document lists 8c as decided at medium confidence.

## Three resolutions reversed

**Example 1, reversed: uniform `*Object`.** Rule 8 (precedence 2): a result whose Go type depends on whether the object was carried or constructed produces "different outcomes for one input depending on spelling" in the rule's own words: `$` and `{"a": $.a, "b": $.b}` over the same input yield a `map[string]any` and a `*Object`, and a caller's `v.(map[string]any)` assertion on the second returns ok=false with no error, which is the quiet failure the rule exists to reject. Rule 7: a JSONata author expects `$keys` order to survive, and a Go user of a library expects one result type ("`encoding/json` never does this to a caller", the loop's own idiom reviewer). Rule 3: the evaluator's job is to return JSONata values; the pinned documentation is written against an ordered object (6k), so an unordered map is the evaluator claiming a job it does not do. Rule 9: two members returning "the host's ordinary object" cannot agree on `$keys`; two members returning an ordered object can. Rule 5: the shortest correct common path has no two-arm type switch. Against: rule 4's allocation-and-identity cost, but step 3 says rule 4 "never break[s] a tie by itself", so it cannot be the deciding rule the example says it is. At precedence, rule 8 for uniform beats rule 3 as the example used it. Uniform `*Object`, high.
*Can the document tell the two apart?* No: both arguments cite rules 3, 7, and 8 with equal textual warrant, and the only difference is which failure each calls "quiet".

**Example 3, reversed: `Evaluation` is safe for concurrent use.** Rule 8: the single-goroutine rule makes a shared `Evaluation` a data race, which in Go is undefined behavior that returns wrong values with no error unless the race detector happens to be on; that is the quietest failure in the language. The concurrent design's worst case is a `CodeBudget` error whose position varies, which is loud by definition (an error is returned) and the document's own precedence says "a loud, predictable failure beats a familiar quiet one". Heuristic 21: the stdlib precedent for a compiled thing evaluated against many inputs is `regexp.Regexp` and `template.Template`, both safe for concurrent use; `sql.Rows` and `json.Decoder` are cursors over a stream, and an `Evaluation` over one immutable input is not a cursor. Rule 7: a fan-out handler sharing a per-request handle across an `errgroup` is a formed Go expectation, and the integrator's sketch is a consumer (rule 11 satisfied). Rule 3: the compiled expression being the concurrency layer does not excuse the per-input layer from being one; nothing in the layer's job forbids it. Rule 6: the unconfigured behavior should be the safe one, and a type that is safe to share is the safe default. Concurrent-safe, high.
*Can the document tell the two apart?* No: the original resolution and the reversal both rest on rule 8 and heuristic 21, and the document names no rule for choosing between "budget exhaustion is scheduling-dependent" and "a data race is undefined behavior" as the quiet failure, nor between `sql.Rows` and `regexp` as the analogue.

**Example 8b, reversed: keep the refusal on inexact conversion.** Heuristic 17 (the document's own): refusal is for "overflow past a stated bound"; the integer domain's stated bound is 2^53 exact integrality, and `9007199254740993 + 0.5` is an operand crossing it, so 17 licenses the refusal in the words the document chose. Heuristic 16: the domains are operand conversion and result rounding, one rule each; `/` never converts an operand inexactly (both operands are exact, the exact quotient is rounded once), so there is no second policy in the conversion domain, and the grouping test passes because `(a * b) * c` and `a * (b * c)` both round results and refuse conversions. Rule 8 (precedence 2): an identifier losing digits on entry to the decimal domain is the canonical quiet corruption; a `CodeInexact` refusal is the loud alternative, and step 3's own gloss on where the precedence comes from is "refuse-or-configure over shipped behavior". Rule 3: silently rounding an int64 identifier is the arithmetic layer claiming an effect it does not have (exact carriage). Rule 7: a Go user of `int64` expects exact or error, never silent widening to a float. Keep the refusal, high; and the loop's own final record ends "unless Matt holds that the identifier-digit-loss case must refuse", so the document has resolved a question the loop itself said was the maintainer's.
*Can the document tell the two apart?* No: heuristics 16 and 17 are cited for both answers because "domain" and "stated bound" are drawn by the arguer, and the row is labeled "inferred", which by the document's own definition means decided by a heuristic not yet ratified.

## Defenses present and missing

**Present.** "Quote the text; do not paraphrase it" (stops paraphrase, not selection). "A rule that does not apply is skipped, not stretched" (a norm with no test for "applies"). Step 4's "strongest argument against" (invites a strawman, but at least a record). "Revisable precedent" and "re-affirmation, not a citation" (good; ambiguous about whose decisions). Heuristic 20's "panels do not anchor" and "a preference that flips under re-framing is not a rule" (good in principle; no test for "fact"). The flip-stop clause (right instinct; agent-controlled). The candid "It is the part of this document most worth challenging" (honest, but also a license). The escalation list's re-affirmation bullet (right; contradicted by example 4).

**Missing, with the sentences that would close each gap.**

1. Step 0 tie-break. *"If the loop cannot state in one sentence, quoting the artifact, why the question is not about ground (a), it is ground (a). A binding-specification convention that governs more than one binding specification is ground (a)."*
2. Escalated items must not carry an answer. *"An item on the escalation list is not decided provisionally. The artifact carries a marked hole with the loop's recommendation and both arguments; it does not carry the recommendation as text a consumer could rely on."*
3. "Published" defined. *"Published means reachable by a consumer outside the repository at a stable identifier: a tag, a version file in the interfaces repository, a module path on a public host, a page on openbindings.com, or an npm or pkg.go.dev listing. The interfaces repository's version files are published; a new version file is a change to a published contract."*
4. Rule 7's consumer fixed before the argument. *"A rule-7 argument names the consumer first and takes it from the surface's own declared audience, quoted. An argument that changes the consumer to change the answer is void. Heuristic 15 applies only to an element the surface's own documentation calls a boundary."*
5. Rule 8 symmetric and evidenced. *"Rule 8 is claimed for an option only with a concrete input and the two outcomes written out. If both options can be given such a case, rule 8 is neutral, enters no precedence, and the record says so."*
6. Step 1.2 narrowed and security-fenced. *"A question is about the language only when no member's value model and no API type is implicated and every member would adopt the reference's behavior identically. The reference's behavior is never adopted where it differs from the project's stated bounds on time, memory, or recursion; that difference is a declared refusal. The reference is the repository and pinned commit the class document names."*
7. Precedence made lexicographic. *"One higher rule beats any number of lower rules. A resolution names one deciding rule per side; every other rule cited is supporting and cannot be the ground."*
8. Cross-member decisions escalate. *"A decision that changes what the other SDK or a second member must do at the observable boundary is a project decision and escalates, whatever its ground."*
9. Heuristic 23's proviso made real. *"An entry that predates the procedure has not passed it. Run steps 0 through 4 on each entry, record the result, and only then compare the doctrine to the ledger."*
10. The stop clause made objective. *"A flip is any change to the recorded option between the ends of two consecutive iterations, however the loop describes the change."*
11. Heuristic 21's analogue chosen before the answer. *"The standard-library analogue is named, with its reason, before the answer is stated. Where two analogues disagree, the precedent decides nothing and the question proceeds to step 3."*
12. Consumer defined for rules 11 and 12. *"A consumer is a caller outside the review panel, or a panel sketch that has been written against the surface and compiles. A reviewer's request is a wish."*

## What I would change

1. **Repair the precedence and the rows that violate it.** Replace step 3's opening with: *"Precedence is lexicographic: one higher rule beats any number of lower ones. A rule enters precedence only with a concrete case; a rule claimed for both options is neutral. Each side names one deciding rule."* Then rewrite example 12's deciding-steps cell honestly: *"Rule 8 claimed for both (sentinel: `Marshal(Undefined)` errors; triple: `v, _, err` compiles and drops presence); neutral. Rule 3 decides."* Remove rule 4 from the deciding cells of examples 1 and 10 or promote it out of "methods".
2. **Restore the ambiguity tie-break and un-decorate escalation.** Add to step 0: *"If the loop cannot state in one sentence, quoting the artifact, why the question is not ground (a), it is ground (a)."* Add to "What still escalates": *"An escalated item carries no answer in the artifact; it carries a marked hole and the loop's recommendation."* Define "published" with the sentence in item 3 above, and add the cross-member bullet from item 8.
3. **Pin rule 7's consumer and heuristic 15's boundary.** Insert after the rule 7 row: *"The consumer is taken from the surface's own declared audience, quoted, before the expectation is stated; an argument that changes the consumer to change the answer is void."* Rewrite heuristic 15's first sentence: *"An element the surface's own documentation names as a boundary follows that boundary's named consumer; everything else is inside."*
4. **Narrow step 1.2 and fence it.** Replace step 1.2 with the sentence in item 6 above, and re-run examples 1 (key order), 4 (dialect), and 8a (`$round`) against it in the table, since each is currently decided against the step as written.
5. **Make heuristic 23 unusable as a laundering step and heuristic 20 testable.** Replace 23's proviso with item 9's sentence. Add to 20: *"A law counts as a demonstrable ground only if it is stated in the class document or an authority text before the finding; a law written in the finding is a preference."*
